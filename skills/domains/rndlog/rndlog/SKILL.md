# R&D 증빙 서류 작성

세액공제를 받으려면 연구가 실제로 있었다는 기록이 남아 있어야 한다. 이 스킬은 그 기록을
회사별로 만들어 낸다. 산출물은 과세당국과 KOITA가 읽는 문서이므로, 지어낸 사실을 넣으면
가산세와 인정 취소로 돌아온다.

## 실행 위치

- 중앙 조정실에서 스킬을 읽고 `chaconne@49.247.207.147`에 SSH로 접속해 작업한다.
- 실제 작업 공간은 운영 서버의 `/home/chaconne/rndlog/clients/`다. 아래 상대 경로는 모두
  `/home/chaconne/rndlog` 기준이다.
- 중앙 서버의 `/home/chaconne/rndlog` 복제본에서 고객 문서를 만들지 않는다.
- 시작 전에 `project/rndlog-operating-context`, 원격 `CONTEXT.md`, `clients/README.md`, 원격 Git
  상태를 확인한다. 기존 변경과 미추적 파일은 다른 작업자의 작업으로 보고 보존한다.

필수 원본이나 확정값이 없으면 생성 단계로 넘어가지 않는다. 빠진 항목과 필요한 제공자를
구체적으로 보고하고, 확인되지 않은 사실이나 수치로 빈칸을 채우지 않는다.

## 진행 순서

여섯 단계를 순서대로 밟는다. 앞 단계의 산출물이 다음 단계의 입력이므로 건너뛰지 않는다.

### 1. 회사 정보 취합

- 입력: `clients/<슬러그>/inputs/`에 받은 원본 — 인정서, 사업자등록증, 회사소개서,
  연구개발개요서, 특허·인증 서류.
- 홈페이지도 함께 조사한다. 제품·서비스·조직·채용공고가 연구 인력과 과제의 근거가 된다.
  현재 내용과 출처 URL을 함께 기록한다.
- 결과는 `clients/<슬러그>/README.md`에 표로 적는다. 최소 항목: 법인명·사업자번호·대표자·
  소재지·사업 내용, 인정 구분과 인정번호·인정일, 연구원 명단과 투입률·연봉, 특허 목록.
- **인정번호와 인정일은 반드시 인정서 원본에서 읽는다.** 이 값이 틀리면 문서 전체가 무효다.

### 2. 연구 유망 기술 선정

회사가 이미 가진 것에서 출발해야 과제가 사후에 부정되지 않는다. 특허·제품·인력과 무관한
주제는 아무리 유망해도 고르지 않는다.

조사할 것:

- 국내외 논문 — 과제의 기술적 근거가 된다. 과제 착수 시점에 최신이라고 말할 수 있는
  것을 고른다. 오래된 연구만 인용하면 이미 확립된 기술을 따라 한 것으로 읽힌다.
- 산업 동향·시장 규모 — 연구개발계획서의 「연구 배경 및 필요성」이 이 숫자를 인용한다.
- 선진업체 사례 — 「기존 기술 대비 차별성」이 비교 대상으로 삼는다.

결과는 `clients/<슬러그>/research/`에 남긴다. 주제는 3~5개를 제안하고 그중 하나를 고른다.
법령·세액공제·KOITA 요건은 저장소 문서만 믿지 말고 현재 공식 자료로 확인한다.

### 3. 기술 자료 취합

고른 주제의 근거 자료를 모은다. 논문은 제목·학술지·연도까지 적는다. 출처 없는 수치는
문서에 넣지 않는다 — 실사에서 근거를 대지 못한다.

### 4. 증빙 풀세트 생성

문서 세트는 회사 상황에 따라 달라진다. 아래 규칙으로 정한다.

| 문서 | 주기 | 조건 |
|---|---|---|
| 연구개발계획서 | 연 1회 | 항상 |
| 연구노트 | **주 1회** | 항상 |
| 업무일지 | **주 1회** | 항상 |
| 인건비배분표 | 분기 | 항상 |
| 연구과제총괄표 | 연 1회 | 항상 |
| 인력개발비명세서 | 연 1회 | 항상 |
| 완료보고서 | 과제 종료 시 | 항상 |
| 회의록 | 분기 | 연구원 2명 이상 |
| 자가점검보고서 | 분기 | **1인 전담부서** — 회의체가 없어 회의록을 갈음한다 |

- 파일명: `<연도>_W<주차 2자리>[_<주제>].html` (주간), `<연도>_Q<분기>.html` (분기),
  `<연도>.html` (연간). 주차는 ISO 기준으로 센다.
- 위치: `clients/<슬러그>/reports/source/<카테고리>/`
- 이 주기는 새로 착수하는 회사에 적용한다. 진행 중인 회사는 그 회사가 이미 쓰던 주기와
  파일명을 이어간다.

문서에 반드시 들어가야 하는 것 — 세무조사에서 이 세 가지가 없으면 연구개발비로 인정받지
못한다:

1. **기술적 불확실성** — 착수 시점에 결과를 알 수 없었다는 서술. "무엇을 몰랐는가"를 적는다.
2. **기존 기술 대비 차별성** — 단순 도입·구매·외주가 아니라는 근거.
3. **시행착오 기록** — 실패한 시도가 연구노트에 남아 있어야 한다. 성공만 적힌 기록은
   연구가 아니라 생산 활동으로 판정된다.

시나리오로 채운 정량 수치(실험값·정확도·모집 인원)는 회사 README에 **실측 아님**을 명시한다.
나중에 실측으로 갱신할 대상을 표시하지 않으면 거짓 기록이 그대로 제출된다.

### 5. 문서 양식

서식은 `clients/_templates/style.css` 하나가 정본이다. 새 CSS를 만들지 않는다.

- 색 팔레트의 출처는 RNDlog 견적서(`assets/name-card/견적서_RNDlog_ver1.0.docx`)다.
- 강조 채움색은 `--primary-bg` 하나뿐이다. 라벨 칸·표 머리·합계행·섹션 제목이 모두 이
  변수를 읽는다. 자리마다 다른 값을 주면 어느 것이 머리글인지 읽히지 않는다.
- 색은 `<body>` 클래스로 고른다 — 클래스가 없으면 견적서와 같은 초록, `theme-blue`는 파랑,
  `theme-gray`는 회색이다. 회사가 원하는 색이 따로 없으면 초록을 쓴다.
- 회사별 작업 시작 시 `_templates/style.css`를 `reports/source/style.css`로 복사한다.
  복사본을 쓰는 이유는 납품 후 공용 서식이 바뀌어도 이미 낸 문서의 모양이 흔들리지 않게
  하기 위해서다.
- 마크업 클래스는 새로 만들지 말고 `docs/samples/html/`의 문서 골격을 그대로 따른다.
  같은 클래스를 써야 서식 하나로 모든 회사 문서가 같은 모양으로 찍힌다.
- 본문에 이모지를 넣지 않는다. PDF 변환이 폰트 서브셋 단계에서 실패해 그 문서만 조용히
  빠진다. 샘플 문서의 타임스탬프 체인에는 이모지가 남아 있으나 그대로 복사하지 말고
  숫자나 기호로 바꾼다.

### 6. PDF 빌드

```bash
ssh chaconne@49.247.207.147 \
  'cd /home/chaconne/rndlog && /home/chaconne/.local/bin/uv run python clients/_scripts/html_to_pdf.py clients/<슬러그>/'
```

렌더러는 WeasyPrint다. 샘플 PDF가 WeasyPrint로 만들어져 있어 다른 렌더러를 쓰면 줄바꿈과
페이지 분리가 달라진다. 브라우저 기반 변환은 쓰지 않는다.

## 마무리

- `clients/<슬러그>/README.md`의 산출 이력에 작성일·산출물·위치를 추가한다.
- `clients/README.md`의 등록 회사 표를 갱신한다.
- 새로 알아낸 제도 규정은 `docs/research/기업부설연구소관리.md`에 반영한다.

## 금지

- `inputs/`의 회사 제공 원본을 고치지 않는다. 받은 그대로 두어야 대조 근거가 된다.
- 출처 없는 수치·논문·기관명을 문서에 넣지 않는다.
- 연구원 명단에 실제 근무하지 않는 사람을 넣지 않는다. 인건비 부인과 인정 취소 사유다.
- 이미 제출한 문서를 새 규칙에 맞춰 다시 만들지 않는다. 회사가 낸 것과 우리가 보관한 것이
  갈리면 실사에서 어느 쪽이 진본인지 설명하지 못한다.
