# RNDLOG 자료·연구·DOCX 산출 워크플로우

RNDLOG(R&D LOG / R&D NOTE)는 기업부설연구소와 연구개발전담부서가 정부·세무 점검에 대비하도록
고객 원천자료를 수집하고, 회사·기술 리서치를 거쳐 연구개발계획서·연구노트·연구일지·업무일지·
비용 및 증빙 문서를 DOCX로 작성·검증·보관한다. 이 스킬 하나가 자료 수신부터 최종 산출물까지의
단일 공식 워크플로우다.

## When to Use

- 카카오톡 등에서 RNDLOG 고객 자료를 수집할 때
- 신규 회사를 메인서버 작업공간에 등록할 때
- 연구주제·논문·시장·제도 자료를 조사할 때
- 연구개발계획서, 연구노트, 업무일지와 증빙 DOCX를 만들거나 갱신할 때
- 운영서버에 남은 고객 자료·리서치·산출물을 메인서버로 회수할 때

웹제품 화면·Django 템플릿·Tailwind·HTMX 작업에는 `rndlog-design-system`을 사용한다. 웹 UI 디자인과
고객 DOCX 보고서 스타일을 섞지 않는다.

/home/chaconne/projects/rndlog/

│   │   ├── README.md

└── 자료/
    └── <사업자등록증의 정식 회사명>/
        ├── README.md                     # 회사 메타·자료·조사·산출 이력
        ├── inputs/                       # 고객 원천자료와 수신메모, 불변
        ├── research/                     # 회사별 조사와 출처
        └── reports/
            ├── source/                   # 편집·검토 중인 DOCX
            ├── output/                   # 검증 완료 DOCX 정본

회사 폴더는 채팅방 이름·프로젝트 가칭·영문 슬러그가 아니라 사업자등록증의 정식 법인명을 사용한다.

## 단일 공식 워크플로우

### 0. 시작 전 상태 확인

1. 메인 프로젝트 `AGENTS.md`, `README.md`, 이 스킬과 GBrain 운영맥락을 읽는다.
2. 메인서버 회사 폴더와 운영서버에 동일 자료가 있는지 확인한다.
3. 기존 파일은 다른 작업자의 작업으로 보고 덮어쓰거나 삭제하지 않는다.
4. 회사의 정식 법인명을 확인할 원본이 없으면 임시 회사 폴더를 만들지 말고 확인을 요청한다.

완료 기준: 대상 회사, 자료 출처, 정본 저장 위치가 하나로 잠긴다.

### 1. 카카오톡 자료 수집

1. Windows에서 지정된 카카오톡 채팅방의 오늘 날짜 구간을 확인한다.
2. 첨부파일 카드, 이미지, URL, 링크 카드와 “추가 첨부 예정” 메시지를 모두 구분한다.
3. 미다운로드 첨부는 카카오톡의 `저장` 동작으로 내려받는다.
4. 실제 다운로드 위치 `C:\Users\chaconne\Documents\카카오톡 받은 파일`에서 파일명·크기·수정시각을 확인한다.
5. 받은파일 폴더만 보지 말고 채팅방 파일 카드를 끝까지 확인한다. 다운로드되지 않은 카드는 폴더에 나타나지 않는다.
6. 메시지를 보내거나 채팅·파일을 삭제하지 않는다.

완료 기준: 오늘 수신한 첨부·링크·미수신 예정자료가 각각 목록화된다.

### 2. 회사 식별과 수신기록

1. 사업자등록증에서 법인명·사업자번호·대표자·주소를 읽는다.
2. 채팅방 이름과 법인명이 다르면 법인명을 회사 폴더명으로 사용한다.
3. OCR 텍스트가 중복·모호하면 원본 이미지를 육안 대조하고, 확인 전에는 그대로 확정하지 않는다.
4. `inputs/YYYY-MM-DD_수신메모.md`에 수신일, 채팅방, 받은 파일, 링크, 예정됐으나 미수신인 자료를 기록한다.

완료 기준: 모든 원천파일이 정확한 법인과 수신기록에 연결된다.

### 3. 메인서버 적재

1. `/home/chaconne/projects/rndlog/자료/<정식 회사명>/` 아래 표준 폴더를 만든다.
2. 파일은 `inputs/`에 원래 파일명과 바이트를 유지해 복사한다.
3. 같은 이름의 기존 파일이 있으면 덮어쓰지 않는다. SHA-256이 같으면 중복으로 기록만 하고, 다르면 날짜·버전을 구분해 둘 다 보존한다.
4. Windows 원본과 메인서버 파일의 크기·SHA-256을 비교한다.
5. 링크는 수신메모 또는 `inputs/링크.txt`에 한 줄씩 기록하고 다시 읽어 검증한다.

완료 기준: 원천파일 수, 누락 목록, 해시 불일치가 각각 명시되고 불일치가 0건이다.

### 4. 회사 README 등록·갱신

README에는 최소한 다음을 둔다.

- 법인명, 사업자번호, 법인번호, 대표자, 소재지, 사업 내용과 확인 근거
- 연구소/전담부서 구분, 인정번호·인정일·부서명
- 연구원 명단, 직위, 학위·전공, 입사일, 투입률·급여
- 특허·출원·인증 목록
- 원천자료 수신 이력
- 리서치 이력
- DOCX 작업본·최종본 이력과 검토 상태
- 미확정 정보와 필요한 제공자

인정번호와 인정일은 인정서 원본에서만 확정한다. 없는 항목은 비워 두지 말고 `미확정`과 필요한
원본을 명시한다.

완료 기준: README만 읽어도 현재 사실·산출물·누락정보를 파악할 수 있다.

### 5. 생성 가능 문서 판정

자료가 있다고 곧바로 연구노트를 만들지 않는다.

| 현재 확보 자료 | 생성 가능한 산출물 |
|---|---|
| 사업자등록증 등 회사 기본자료만 있음 | 착수 현황 및 자료 검토 보고서 |
| 인정서·연구원·연구개요가 있음 | 연구과제 후보와 연구개발계획서 초안 |
| 실제 주간 연구활동 원자료가 있음 | 해당 기간 연구노트·연구일지·업무일지 |
| 인건비·투입률 원자료가 있음 | 인건비배분표·인력개발비명세서 |
| 과제 종료 실적과 결과가 있음 | 완료보고서 |

필수 원본이 없으면 상위 단계 문서를 지어내지 않고, 현재 생성 가능한 착수·누락자료 보고서만 만든다.

완료 기준: 이번 실행에서 만들 문서와 만들 수 없는 문서가 근거와 함께 분리된다.

### 6. 회사·기술·제도 리서치

1. 회사 제품·서비스·조직·채용공고와 홈페이지를 조사한다.
2. 보유 특허·제품·인력에서 출발하는 연구주제 3~5개를 제안한다.
3. 국내외 논문은 제목·저자·학술지·연도·DOI/URL을 기록한다.
4. 시장·제도 자료는 기관·문서명·발행일·URL·확인일을 기록한다.
5. 법령·세액공제·KOITA 요건은 현재 공식 자료로 다시 확인한다.
6. 결과는 `research/`에 저장하고 출처 없는 수치를 넣지 않는다.

완료 기준: 보고서 핵심 주장마다 원천자료 또는 외부 출처가 추적된다.

들어가야 한다. 성공만 있는 가상 연구기록을 만들지 않는다.

완료 기준: 연간·분기·주간 문서 계획이 실제 원자료의 기간과 일치한다.

### 8. DOCX 생성

스타일 참조 정본:

```text
/home/chaconne/projects/rndlog/공통/양식/design-report-reference.docx
```

참조할 것:

- A4에 맞춘 안정적인 여백
- 제목·부제·Heading 1/2/3·본문·캡션의 명확한 위계
- 흑백·회색 중심의 단순한 보고서 인상
- 얇은 표선과 최소한의 음영
- 머리말·꼬리말·페이지 번호와 필요한 경우 목차

복사하지 않을 것:

- `Report title`, `Date`, 영문 목차·본문·placeholder
- 표지 사진과 샘플 프로젝트 이미지
- RNDLOG 웹 UI, 견적서 색상, 카드·인포그래픽·마케팅 표현

생성 규칙:

1. 참조 DOCX는 변경하지 않고 복제·가져오기 방식으로 스타일만 사용한다.
2. `python-docx` 또는 사용 가능한 DOCX 도구로 생성한다. OOXML에 직접 문자열 치환하지 않는다.
3. 참조 이미지 관계와 미디어 파트를 제거한다.
4. 작업본은 `reports/source/<카테고리>/<파일명>.docx`에 저장한다.
5. 주간 파일명은 `<연도>_W<주차 2자리>[_<주제>].docx`, 분기는 `<연도>_Q<분기>.docx`, 연간은 `<연도>.docx`를 기본으로 한다.
6. 일반 착수·검토 보고서는 `<YYYY-MM-DD>_<문서명>.docx`로 저장한다.

완료 기준: 샘플 내용·사진이 없고, 확인된 사실과 출처만 들어간 DOCX 작업본이 생성된다.

### 9. DOCX 검증과 최종 확정

1. 본문·표·머리말·꼬리말 텍스트를 다시 추출해 원천자료와 대조한다.
2. `Lorem ipsum`, `Report title`, `Date`, `[Author]`, 영문 샘플 목차와 placeholder가 없는지 DOCX 패키지 전체 XML을 검사한다.
3. ZIP 패키지 무결성, 관계 대상, 미사용 이미지 잔존 여부를 검사한다.
4. Word 또는 LibreOffice로 렌더링해 모든 페이지를 확인한다.
5. 표·문단 잘림, 빈 페이지, 겹침, 지나치게 작은 글자, 부자연스러운 페이지 나눔을 확인한다.
6. 검증을 통과한 작업본만 같은 상대경로의 `reports/output/`으로 복사한다.
7. source와 output의 SHA-256 일치, 최종 DOCX 파일 수와 크기를 확인한다.

PDF는 사용자가 별도로 요구할 때만 검토·전달용 보조 사본으로 만들며 정본으로 취급하지 않는다.

완료 기준: 패키지 검사와 100% 페이지 육안 검토가 통과하고 최종 DOCX가 `reports/output/`에 있다.

### 10. 이력·서버 정리

1. 회사 README에 작성일, 문서명, source/output 위치, 근거자료, 검토 상태를 기록한다.
2. `inputs/` 원본과 `reports/output/` 최종본은 변경하지 않는다. 수정본은 새 버전으로 만든다.
3. 운영서버에서 회수한 고객자료는 메인서버 파일 수·크기·해시를 전수 검증한 뒤 운영서버 사본을 제거한다.
4. 운영서버의 네이티브 도구·플러그인 캐시는 고객자료가 아니므로 임의 삭제하지 않는다.
5. 구조·출력형식·서버 역할이 바뀌면 이 스킬, 프로젝트 `AGENTS.md`·`README.md`, GBrain을 같은 작업에서 갱신한다.
6. 스킬 변경은 kmh-agent-kit GitHub `main`에 PR로 병합하고 메인 조정실의 스킬 링크가 새 정본을 가리키는지 확인한다.

완료 기준: 메인서버만 자료·산출물 정본을 가지고, 운영서버 Git과 파일시스템에 고객자료 사본이 없다.

## Pitfalls

- 카카오톡 받은파일 폴더만 보면 미다운로드 파일 카드를 놓친다.
- 채팅방 이름을 회사명으로 쓰면 여러 회사 자료가 섞인다.
- OCR 중복을 사실로 확정하면 업종·특허 목록이 왜곡된다.
- 사업자등록증만으로 연구개발계획서나 연구노트를 만들면 허위 기록이 된다.
- 참조 DOCX 본문을 지우기만 하면 표지 사진과 `Report title`·`Date` 텍스트박스가 패키지나 머리말에 남을 수 있다.
- DOCX가 열리는 것만으로 검증 완료가 아니다. 패키지 XML과 렌더된 모든 페이지를 확인한다.
- 과거 HTML/PDF는 레거시이며 신규 성공 경로로 되살리지 않는다.
